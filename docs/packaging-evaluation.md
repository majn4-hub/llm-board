# 打包评估：Python 内嵌 vs 纯 Swift 重写

> 评估日期：2026-09-17 · 评估人：维护团队 · 状态：**待决策**（本文只给评估与建议，未动手）
> 背景：llm-board = Python（采集/预测）+ Swift（浮窗）。当前发布形态是「源码运行」：用户自建 venv、`pip install -e .`、`swiftc` 编译浮窗。本文评估要不要（以及如何）做成「下载即用」。

## 选项对比

### A. 维持源码运行（现状）

- **体验**：开发者友好；对非开发用户有门槛（Python ≥ 3.11 + 终端操作）。
- **成本**：0。**风险**：0。
- 适用：v0.1 阶段、目标用户是 AI 工具重度用户。

### B. Python 内嵌（.app 内置解释器/依赖）

- **做法**：把 Python 解释器 + 依赖 + 本项目打进 `.app`（PyInstaller / py2app / 手工 bundle + 内置 venv），Swift 浮窗作为 UI 层。
- **成本**：1–2 天（含构建脚本）；分发需 **代码签名 + 公证**（前提：Apple 开发者账号，¥688/年，需确认是否具备）。
- **体积**：约 60–120 MB。
- **风险**：中——bundling 细节（动态库、无窗口启动、PATH）；但**算法实现保持单一**。
- 适用：想给泛用户「双击即用」。

### C. 纯 Swift 重写（采集 + 预测全部 Swift 化）

- **做法**：把 Python 侧约 1300 行（5 个 provider、codexbar 子进程、代理探测、SQLite 历史库、归因、报告渲染）全部移植到 Swift。
- **成本**：采集器 1.5–2 天 + 预测/归因 1–1.5 天 + SQLite/子进程/代理细节 0.5–1 天 + 单测与「新老回放对比」回归 0.5–1 天 ≈ **3–5 个专注工作日**（另需公证流程）。
- **体积**：单二进制，约 3–6 MB。
- **风险**：**高**——把全部算法细节（见 `docs/pitfalls.md` 的 12 条）用第二种语言重写一遍 = 把坑重踩一遍；且过渡期双实现并存，维护成本×2。
- 适用：只有当「Python 运行时」被证明是真实采用障碍时才值得。

### D. 内置独立 Python（python-build-standalone，推荐给「下载即用」）

- **做法**：随包携带一个独立 Python 构建（类似 uv 的做法，压缩后 ~25–50 MB），而非系统 Python；启动脚本用它跑本项目。
- **成本**：1–2 天；同样需要签名/公证。
- **风险**：中低——比 B 更干净（不依赖系统 Python）、比 C 便宜得多；算法实现保持单一。
- 适用：B 的改良版，若做「下载即用」优先此方案。

## 工作量与风险总表

| 选项 | 开发 | 分发（签名/公证） | 体积 | 算法风险 | 长期维护 |
|---|---|---|---|---|---|
| A 现状 | 0 | 无 | — | 无 | 低（单语言） |
| B 内嵌 | 1–2 天 | 需（开发者账号） | 60–120 MB | 低 | 中 |
| C 重写 | **3–5 天** | 需 | 3–6 MB | **高（重踩坑）** | **高（双实现期）** |
| D standalone | 1–2 天 | 需 | ~25–50 MB+ | 低 | 低–中 |

## 建议

1. **v0.1 以 A（源码运行）发布**——零打包风险，先验证需求；README 已把安装压缩到 4 条命令。
2. **若「下载即用」成为真实诉求：走 D（或 B），不走 C。** 核心判断：本产品的差异化是预测/归因算法（12 条技术坑全部在这条链上），**用第二种语言重写算法 = 系统性重踩全部坑 + 此后永久双语言维护**；内嵌/独立 Python 保留单一算法实现。
3. 如果最终仍需纯 Swift（例如强需求：无 Python、极小体积）：按 C 的估算 3–5 个工作日执行，并把「新老回放对比」列为验收硬条件（需在 Swift 侧重建同款对比）。
